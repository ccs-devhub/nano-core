* What is a module?
  A module is a plain object (the file's default export) that bundles
  slash commands, gateway event listeners, lifecycle hooks, and an
  optional health check. The core is MPL-2.0; modules may use *any
  license* (declare it in the =license= field and your repo).

  The core already provides the whole bot surface — every connection,
  service, and API wrapper. A module never wires anything; it only
  *uses* what the core exposes. That gives every module a *kind*:

  | =extension= | Core capability, no slash commands (e.g. mcp)       |
  | =command=   | Slash commands only (e.g. embed-styler)             |
  | =hybrid=    | Commands plus events/tasks (e.g. synapse)           |

  Declare it with the optional =kind= field or let the core derive it
  from the contents. Not every module needs commands.

* The contract
  #+begin_src typescript
  import type { NanoModule } from '@ccs-devhub/nano-core';

  const MODULE: NanoModule = {
    name: 'my-module',          // unique, kebab-case
    version: '0.1.0',
    description: 'What it does.',
    license: 'MIT',
    kind: 'hybrid',             // optional: extension | command | hybrid
    commands: [{
      data: /* SlashCommandBuilder */ undefined as never,
      cooldown: { scope: 'user', delay_ms: 5000, limit: 2 }, // optional
      defer: true,              // optional: dispatcher defers; use editReply
      async execute(interaction) {},
      async autocomplete(interaction) {},  // optional; respond() in <3s
    }],
    events: [{
      name: 'guildMemberAdd',
      intents: ['GuildMembers'],  // declared intents derive the Client set
      execute(...args) {},
    }],
    components: {               // button/select/modal handlers routed by
      rescan(interaction, args) {},  // customIds `my-module:rescan:...args`
    },
    tasks: {                    // named handlers for persistent one-shots
      remind(payload) {},
    },
    onEnable(bot) {},           // runs on registration (if enabled) and /module enable
    onDisable(bot) {},          // runs on /module disable and removal
    healthCheck(bot) {          // optional; feeds /module health
      return { status: 'healthy' };  // healthy | degraded | down
    },
  };

  export default MODULE;
  #+end_src

* Core utilities available to modules
  Everything is imported from =@ccs-devhub/nano-core= — the package
  name resolves everywhere, including the bundled =modules/= folder
  (tsconfig maps it to =src/lib/index.ts=). All API helpers take
  plain ids, return
  =NanoResult<T>= envelopes (={ ok, data | error }=), and produce
  JSON-friendly summaries — deliberately easy to expose to an AI or MCP
  tool layer.

  - =guild=: =listGuilds=, =getGuild=, =getGuildSnapshot= (full server map:
    channels + roles + counts)
  - =channel=: =listChannels=, =getChannel=, =createChannel=, =editChannel=,
    =deleteChannel=
  - =role=: =listRoles=, =getRole=, =createRole=, =editRole=, =deleteRole=,
    =addRoleToMember=, =removeRoleFromMember=
  - =member=: =getMember=, =listMembers=, =kickMember=, =banMember=,
    =unbanMember=, =timeoutMember=, =setNickname=
  - =message=: =sendMessage=, =editMessage=, =deleteMessage=,
    =bulkDeleteMessages=, =fetchMessages=, =pinMessage=, =unpinMessage=,
    =reactToMessage=, =removeOwnReaction= — payloads carry =content=,
    a themed =embed= spec, =files= (URLs or local paths), =reply_to=,
    and =poll= in any mix
  - =dm=: =sendDirectMessage=
  - =thread=: =createThread=, =listThreads=, =setThreadArchived=
  - =webhook=: =createWebhook=, =listWebhooks=, =sendWebhookMessage=
    (optional name/avatar mask), =deleteWebhook=
  - =invite=: =createInvite=, =listInvites=, =deleteInvite=
  - =emoji=: =listEmojis=, =listStickers=
  - =scheduled-event=: =listScheduledEvents=, =createScheduledEvent=
    (voice or external), =deleteScheduledEvent=
  - =guild extras=: =listBans=, =fetchAuditLog=
  - =presence=: =setBotPresence= (bot status + activity line)
  - =embed / theme=: =buildEmbed(spec, theme?)=, =registerTheme=,
    =getTheme=, =listThemes= — style modules register palettes on
    =onEnable=.
  - =embed templates=: =registerEmbedTemplate=, =getEmbedTemplate=,
    =listEmbedTemplates=, =renderEmbedTemplate(name, slots,
    overrides)=, =fillTemplateSlots= — a template is a named
    EmbedSpec whose strings hold ={{slot}}= placeholders. The core
    ships =default=; embed-styler ships five more. Register yours on
    =onEnable= (like themes).

* Installing and managing modules
  #+begin_src shell
  # one-command install (npm package or local path)
  npm run module -- add @scope/nano-module-x
  npm run module -- add ./modules/my-local-module

  # manage
  npm run module -- list
  npm run module -- disable my-module
  npm run module -- enable my-module
  npm run module -- remove @scope/nano-module-x
  #+end_src

  Entries live in =nano.config.json= (=modules= array; npm package names
  or local paths). Runtime management is also available in Discord via
  =/module list|enable|disable|health|sync= (administrator only). After
  enabling or disabling, run =/module sync= to update the registered
  slash commands.

** Module dependencies
   A module may declare its own npm =dependencies= in its
   =package.json= (nano-core >= 0.2.1). The store installer runs
   =npm install --omit=dev --ignore-scripts= inside the module folder
   after a github install or update, so imports resolve from the
   module's own =node_modules= (Node walks up from the module file).
   If that install fails the module is kept and a warning explains the
   manual command. npm-sourced modules get dependencies from npm
   itself. Keep dependencies minimal — module code runs with full bot
   privileges, and =--ignore-scripts= means packages needing install
   scripts will not work.

* Rules the registry enforces
  - Module names and command names must be unique; duplicate commands
    are skipped with a warning.
  - Disabled modules keep their listeners bound but gated: events do
    not fire and commands answer with a disabled notice.
  - The =nano= kernel module (dispatcher, =/module= manager) is protected
    and can never be disabled or removed.
  - A module that fails to import is logged and skipped; it never
    prevents the bot from starting.

* Gateway intents and events
  Every discord.js Client event is already wired: declare a listener
  in =events= with the event =name= and the =intents= it needs, and
  the core derives the Client intent set at boot — a module never
  touches the Client. The host can also force intents in
  =nano.config.json= (=intents= array). =Guilds= is always included.
  Privileged intents (=GuildMembers=, =GuildPresences=,
  =MessageContent=) additionally need the developer-portal toggle;
  boot and =npm run doctor= verify the toggles via the application
  flags.

  Common events and the intent each needs:

  | Event                                  | Intent            |
  |----------------------------------------+-------------------|
  | =messageCreate= / =messageDelete=      | =GuildMessages= (+ =MessageContent= to read text) |
  | =messageReactionAdd= / =Remove=        | =GuildMessageReactions= |
  | =guildMemberAdd= / =Remove= / =Update= | =GuildMembers= (privileged) |
  | =presenceUpdate=                       | =GuildPresences= (privileged) |
  | =voiceStateUpdate=                     | =GuildVoiceStates= |
  | =channelCreate= / =Delete= / =roleCreate= / =guildUpdate= ... | =Guilds= |
  | =guildBanAdd= / =guildBanRemove=       | =GuildModeration=  |
  | =inviteCreate= / =inviteDelete=        | =GuildInvites=     |
  | =threadCreate= / =threadUpdate=        | =Guilds=           |
  | =guildScheduledEventCreate= ...        | =GuildScheduledEvents= |
  | =typingStart=                          | =GuildMessageTyping= |
  | =interactionCreate=, =ready=           | none (always delivered) |

  Any event name from the discord.js Client works — the table is the
  common subset, not a limit.
